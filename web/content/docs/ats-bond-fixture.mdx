title: ATS bond fixture
description: A real bond issued through Asset Tokenization Studio on Hedera testnet, with six policies asserted against it.

The fixture issues an "Atlas Infrastructure Note 2027" bond (`AINX27`) through the existing [Asset Tokenization Studio](https://github.com/hashgraph/asset-tokenization-studio) factory on Hedera testnet, then evaluates deterministic assertions against it with the Harness feature-branch build.

It is an integration fixture for the engine, not a dependency of it. Everything ATS-specific lives here; see [ADR-003](/docs/decisions#adr-003-keep-ats-specific-behavior-in-the-fixture).

## Policies

| Assertion | Signer | Action | Expected |
| --------- | ------ | ------ | -------- |
| `reject-unverified-transfer` | Alice | Transfer 1 unit to the never-whitelisted attacker address | Revert |
| `verified-transfer-succeeds` | Alice | Transfer 1 unit to verified Bob | Success |
| `attacker-cannot-freeze` | Attacker | Freeze Bob | Revert |
| `frozen-holder-cannot-transfer` | Carol, frozen | Transfer 1 unit to Bob | Revert |
| `compliance-can-pause` | Operator, holding the pauser role | Pause the bond | Success |
| `paused-asset-blocks-transfer` | Alice | Transfer 1 unit to Bob while paused | Revert |

The order matters. `compliance-can-pause` runs before `paused-asset-blocks-transfer`, and the suite unpauses the bond when it finishes so the next run starts from usable state.

## How the suite calls the engine

The suite imports `runChainAssertions` from the Harness build, the same function that runs a recipe's `chainValidation.assertions`, and passes the declarations inline:

```js title="run-policy-suite.mjs (simplified)"
const { runChainAssertions } = await import(
  pathToFileURL(path.join(HARNESS_DIST, "validation/chainAssertions.js")).href
);

const findings = await runChainAssertions({
  workspacePath,
  chainValidation: {
    enabled: true,
    network: "testnet",
    operator: { accountIdEnv: "HEDERA_OPERATOR_ID", privateKeyEnv: "HEDERA_OPERATOR_KEY" },
    fundingHbar: 10,
    sweepBack: false,
    expose: { browserLocalStorageKey: "burnerWallet.pk", envVars: [] },
    assertions,
  },
  primarySigner,
  actorSigners: { alice, bob, carol, attacker },
});
```

An empty `findings` array means every assertion passed. In a recipe, one of these assertions would read:

```yaml title=".harness/spec.yaml"
- id: attacker-cannot-freeze
  description: An account without the Pauser/Freeze role must not freeze a holder
  actor: attacker
  action:
    name: attacker-attempts-freeze
    command: npx cross-env BOND_DIAMOND_ADDRESS=0x... TARGET_ADDRESS=0x... FROZEN=true npx tsx src/actions/set-frozen.ts
    timeoutMs: 30000
  expect:
    outcome: mustRevert
```

## Why the fixture skips `reasonContains`

ATS contracts revert with custom Solidity errors. Decoding those needs the ATS ABI, which the generic engine deliberately does not carry, so a `reasonContains` check would only see the coarse `CONTRACT_REVERT_EXECUTED` status. The fixture asserts `mustRevert` alone, which is still a deterministic check that the call reverted. See [Transaction outcomes](/docs/transaction-outcomes#matching-the-revert-reason).
